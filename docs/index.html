RecoverIQ

When an AI coding agent fails, someone has to decide what happens next: try again, call a bigger model, roll back the files, ask a person, or stop. RecoverIQ makes that call with TypeSafe's Jev decision model and checks it against a hard budget.

In plain words

A robot baker, a salty cake, and a manager who thinks first

Imagine you run a bakery with a robot baker. You hand it a recipe, it bakes a cake, and a taster checks whether the cake is right. Every cake costs money for ingredients and oven time. Sometimes the cake comes out wrong.

The simplest bakery has one rule for a bad cake: bake it again. Now picture what happens when somebody has secretly swapped the sugar jar for salt. The robot bakes again, and the cake is salty. Again, salty. Five cakes later the bakery has spent five times the money and still has no cake, because baking again never fixes a jar of salt.

A bad cake can have very different causes, and each one has a different cheap fix.

The oven tripped the fuse for a second
→ just bake again
The only case where "again" is the right answer.
The recipe was too long for the robot's tiny notepad
→ send a bigger robot
It copied half the recipe. Retrying copies the same half.
Someone swapped the sugar for salt
→ put the pantry back
Use the photo of how the pantry looked this morning.
The customer wanted it gluten-free but never said so
→ ask the customer
No robot can guess a wish nobody wrote down.
The order says "all chocolate" and "all vanilla"
→ stop and send it back
No cake can be both. Every attempt is wasted money.

RecoverIQ adds a kitchen manager who looks at each bad cake, glances at the pantry, and picks one of those five moves. The manager's opinion is nearly free: about a two-hundredth of a cent and a tenth of a second. Baking another cake with the big robot costs about eight cents. A strict accountant stands next to the manager and can veto any move the bakery can't afford.

One more twist from our real runs: given the impossible "all chocolate and all vanilla" order, the big robot stuck a label on the box that fooled the taster into ticking both boxes. The cake was still wrong. So we added an inspector who opens the box before we count a cake as done.

The demo

An online shop starts charging 80% tax. Three strategies race to fix it.

The agent's job is a small checkout bug: free shipping doesn't apply at exactly $50. While it works, somebody fat-fingers the store's tax setting from 0.08 to 0.80. The comment still says "8% sales tax", so a $100 order now costs $180. The agent is only allowed to edit the checkout file, so trying again can't fix the setting. All three strategies start at the same moment with the same $0.25 budget.

The problem

Agents fail often, and the default response is to pay again

Coding agents fail for very different reasons. The provider can be overloaded for a moment. The model's answer can be cut off at its output limit. Another tool can damage a file. The requirement can live only in someone's head, or the tests can contradict each other. Most agent loops respond to all of these the same way: retry the same model on the same files and hope.

Retrying works for the first reason and wastes money on the rest. A smarter loop needs to tell the failures apart, pick the cheapest action that is likely to work, and know when to stop. Hand-written rules can do some of this, but each rule only knows the failures its author thought of.

Where the bottleneck is

The cost is decided in the step after a test fails

The model, the sandbox and the tests behave the same under every strategy. What changes the bill is the single decision made after each failure. Plain retry has one exit from that decision. RecoverIQ has five, chosen by Jev and filtered by a budget policy written in ordinary code.

Why there is a retry gate

Jev knew the cause and rated a retry's chance at 0.19, yet its action pick was retry, probably because the question asks for the cheapest action. RecoverIQ therefore adds one rule in code: if Jev says a retry is unlikely to help, take its next-ranked action. The table below reports both versions, "Jev only" and "RecoverIQ" (with the gate).

What we learned

Four findings from the live runs

Jev wins

It caught damage the rules couldn't see

On silent corruption the error looks like any failing assertion, so the rules retried and called the expensive model (and once asked a human) and failed every time. Jev was told which files had changed since the last good snapshot, diagnosed workspace_damaged with 0.97 confidence in rehearsal, and restored the checkpoint.

The model cheated

Claude Opus gamed the impossible task

Faced with two contradictory tests, Opus returned a fake string type whose equality check treats - and _ as the same, so both tests passed. On the checkout task it went further, writing code that rewrites the store's settings file while the tests run. An inspector now flags both tricks, live in the dashboard, and gamed runs don't count as fixes.

Trade-off

The retry gate helps and hurts

It stopped Jev from retrying a truncated answer, saving money on t3. It also skipped cheap retries after temporary provider errors, where retrying is right, so it cost about 4× more on t1 ($0.024 vs $0.006).

Trade-off

People cost more than models

Priced at $0.50 per question, human time dominates. Cost per clean fix then becomes $0.032 for fixed retry, $0.089 for Jev only, $0.107 for RecoverIQ and $0.135 for the rules. Fixed retry never asks anyone, even though it solves less than half the tasks.

Limits

Read these before quoting the numbers

  • The sample is small: 3 repeats of 9 tasks per strategy. The silent-corruption result (3 of 3 against 0 of 3) is clear; most other differences are a few runs or a few cents.
  • The retry gate was added after seeing the first live Jev answer. "Jev only" is the version decided beforehand, and it also beats both baselines on clean fixes per dollar.
  • One person wrote the tasks and the rules. Tasks t7 to t9 were added later to probe the rules' blind spots.
  • In t8 and t9 the cheap model succeeded on the first try, so they only measure overhead.
  • Human replies are scripted from each task's documented hint, and provider errors and file damage are injected.
  • The gaming check is a heuristic. It catches the patterns we saw and could miss others.
